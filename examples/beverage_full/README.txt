完整十二阶段饮料生产线：example4 / example5

这是当前三口味、多规格模拟生产线的完整工艺版，已同时更新单体 JSON 和四层结构。
example4：橙汁、苹果汁、葡萄汁 × 2 L 家庭装、330 mL 罐装，共六个配方。
example5：保留上述六个配方，再增加三种口味的 250 mL 小瓶装，共九个配方。
每个配方两批，每批六件。七台步进电机：X、Y1、Y2、Z、Infeed、Closure、Outfeed。
全部21个设备均通过独立 device_registry.json 指定端口和站地址；L1仅存 Modbus PDU，不重复站地址或CRC。

L4 仍只传入 [口味编号, 规格编号]。
口味：0橙汁、1苹果汁、2葡萄汁。规格：0家庭装2L、1罐装330mL、2小瓶250mL。
基线 example4 的配方表只有规格0、1；example5 才加入规格2。
口味选择灌装口，规格选择空容器、冲洗、封口、喷码贴标和成品点位；灌装容量与时间随配方变化。

十二阶段及实际动作
----------------
01 初始化：复位阀门及继电器输出；四定位电机显式触发预置PR0；检查完成、刷新位置、读取报警及状态；等待1秒。
02 空瓶上料：推瓶机构、进料电机、上料传感器、移动至对应空容器点、夹取及抓取传感器检查。
03 瓶位检测：四路位置传感器轮询，缓存状态及产量。
04 瓶内冲洗：进入冲洗点；冲洗5秒，压力>=0.2MPa；消毒3秒，排水3秒；抬升。
05 灌装定位：进入对应口味和规格的灌装点，并检查四路定位反馈。
06 灌装：清流量计、写入配方容量/灌装时间，启动选定灌装头，等待完成；检查累计量与液位；关阀；四次压力>=0.1MPa检查，缓存读数。
07 液位复检：独立检查0x0038–0x003B四路传感器，缓存结果。
08 封口：移动至封口点、供盖、封口电机；封口输出保持3秒；扭矩>=2.0Nm、瓶盖到位检查，缓存扭矩。
09 喷码/贴标：进入喷码贴标点，分别执行喷码和贴标输出脉冲，检查传感器；抬升。
10 成品出料：进入成品点，松夹、推瓶和出料电机，检查出料传感器，缓存并更新计数。
11 CIP清洗：CIP阀和泵循环120秒，检查压力>=0.3MPa；排水30秒，停泵；清水冲洗20秒，关闭阀门。
12 回零待机：复位全部输出，四定位电机显式触发预置PR0、轮询完成、刷新位置；报警复检，进入待机。

01、11、12每个配方运行一次；02–10随每件产品执行，共12次。
普通定位仍只触发PR点号变化的轴；初始化/待机的PR0触发显式执行，不因缓存相同而跳过。
PR表视为在设备调试时预先配置完成，生产中不写PR位置参数。这里的回零是模拟的预置原点移动，不是硬件限位寻零验证。
基线33个生产点位，扩展后49个，XYZ各自仍使用0–15号PR点。

相对旧十二阶段配置的适配
----------------
保留旧冲洗、复检、封口、喷码贴标、CIP等阶段的动作、保持时间、压力/扭矩阈值、寄存器和错误代码。
旧四工位重复灌装改为三种口味中选择一个灌装头、按当前规格灌装一次；原固定500mL检查改为配方容量。
旧电机固定等待改为当前模拟设备的完成轮询；进出料使用现有七电机模型。
旧FC04状态缓存只取0001的高字节会得到0，本版统一修正为读取完整两字节，两种表示均相同。
旧喷码/贴标没有显式保持时间，本版保持该语义；模型中一次请求耗时5ms，因此开/关脉冲为5ms。
本版不是与旧单次四工位原始JSON的逐指令等价迁移，而是恢复十二阶段工艺的多配方模拟案例。

验证范围
----------------
独立解释保存的单体与四层配置，在相同确定性虚拟设备模型中逐条比较带时间戳的完整外部事件：设备端口/地址、PDU、响应、等待、缓存、UI、设备完成和成品记录。
example4六个配方完成72件、37122次Modbus交换；example5九个配方完成108件、49020次交换。逐条轨迹一致，扩展前后原有六个配方的轨迹哈希也相同。
每个阶段集另运行11个故障场景：进料卡住、灌装离线、封口卡住、轴报警、冲洗低压、灌装低压、流量不足、复检液位失败、扭矩不足、喷码超时、CIP低压。
六项额外测试验证缩短冲洗/CIP、漏做液位复检、漏贴标会被检测，扩展只改必要内容，以及未支持的规格在设备I/O之前被拒绝。
实际C++执行器执行六个及九个L4，全部完成12件并验证阶段顺序、参数写入和CIP等待。
C++兼容性检查使用立即就绪、预解码工程量模型；压力/流量/扭矩的真实字节解码由Python协议模型验证，不能将两种模型的请求次数混用。
本例没有连接真实硬件，不能将上述结果当作真实设备工艺标定或任意异常路径的形式证明。

文件与复现
----------------
在仓库根目录一条命令验证全部配置与数据（Python 3.10+，标准库）：
Windows PowerShell：.\verify.ps1
已配置Python的其它环境：
python scripts/verify_beverage_full.py

该命令重新生成并核对配置，执行两组正常/故障模拟及六项测试，从新结果计算行数、覆盖率与增量，并核对版本化报告。
只规范化CRLF/LF换行差异；失败返回非零退出码，不覆盖源配置或版本化报告。新结果保存在 build/beverage-verification/。
默认不运行C++检查；安装CMake、CTest、C++17编译器后可运行：
python scripts/verify_beverage_full.py --cpp
PowerShell也可使用 .\verify.ps1 -Cpp。

example4/legacy、example5/legacy：各配方完整单体JSON。
example4/layered、example5/layered：L1-L4配置。
reports/*_simulation.json：正常及故障验证、时序、哈希、覆盖率和行数。
reports/cpp_*.json：C++引擎兼容性结果及限制。
comparison.json、extension.diff：完整规模和新增规格的准确文件差异。

以下为分项复现命令（一般只需运行上述统一入口）：
python scripts/simulate_beverage_full.py --root examples/beverage_full/example4 --report examples/beverage_full/reports/example4_simulation.json
python scripts/simulate_beverage_full.py --root examples/beverage_full/example5 --report examples/beverage_full/reports/example5_simulation.json
python scripts/test_beverage_full.py
python scripts/summarize_beverage_full.py

加 --traces traces 可导出完整正常及故障JSONL轨迹。
轨迹和可执行文件是生成产物，不纳入Git。此前离线交付包中的traces/包含代表性成对轨迹；从仓库运行时可按上述命令重建。
重新生成配置到空目录：
python scripts/build_beverage_full.py --output regenerated

C++编译及兼容性检查由统一入口的 --cpp 选项完成。
