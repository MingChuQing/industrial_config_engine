250 mL 产品扩展：完整工艺说明与可核对补充材料
================================================

用途与记录关系
--------------
本目录把三种口味的250 mL产品扩展整理为可逐行核对的工艺表，说明瓶子从哪里取、
按什么顺序移动、使用哪个灌装口、怎样封盖和检验，以及最终从哪里出料。
它对应已有的十二阶段模拟产线，不表示重新设计或实际调试了一条生产线。

现有生成记录保存在上一级目录：当时模型只读取prompt.txt和context.json。
context.json提供了已有配方、生产点位表、L4入口、run_recipe接口以及新规格的
工程参数；其他阶段作为固定且可复用的流程依赖，没有把全部阶段实现逐行提供给模型。
因此，当时的任务是扩展给定流程的数据和入口，而不是只凭“增加250 mL”推断全部工艺。

本目录的Excel、完整需求文字和动作表，是在首次生成之后依据已保存配置整理的。
它们没有作为该次历史生成的输入，不改变上一级的prompt.txt、context.json、
raw_response.json或provenance.json，也不把新文件追加入原输入哈希清单。
未来新生成任务应使用generation_input.json和requirements_250ml.txt，并另存新任务的输入、原始输出和来源记录。
本次补充材料的校验和输出重放不调用模型，不表示又完成了一次新的模型生成。

目录内容
--------
process_spec.xlsx       面向读者的完整工艺工作簿，包括配方、点位、设备、阶段和动作等。
process_spec.json       结构化工艺说明，含configuration_documents中的完整候选配置JSON和字段来源。
generation_input.json   事后整理的完整输入包：原六配方基线全部非legacy定义、新工程数据和十二阶段摘要。
workbook_data.json      Excel/CSV共用的工作表数据。
source_manifest.json    抽取来源及哈希清单；不替换原生成记录的provenance.json。
tables/*.csv           工作表数据的文本导出，便于Git审查和逐行比较。
requirements_250ml.txt  连贯的自然语言需求和固定流程说明；这是事后整理版本。
comparison.txt         单体JSON和四层配置的改动范围、行数及验证结果说明。

数值和执行顺序以可追溯的JSON配置为依据。Excel不是另一套独立维护的控制程序，
也不会由当前引擎直接下发给设备；其作用是让人理解、审查并与配置逐项对照。
generation_input.json保留原33点、六配方和固定流程，未包含已生成的九配方候选配置。
process_spec.json及Excel包含九配方候选数据，是人类过程说明和输出对照，不能作为
“未见候选答案”的新生成输入。完整输入包也是事后补充，不改写历史模型输入清单。

怎样阅读完整流程
----------------
工作簿页签为“工艺流程”“250mL动作”“配方参数”“配方路线”“生产点位”“设备接口”、
“操作接口”“通用子过程”“条件与异常”和“增量对比”。先读配方参数与路线，再按工艺流程
和250mL动作阅读；通用子过程、操作接口和条件与异常解释每个调用的具体行为：
  01 初始化：关闭输出、四个定位电机回零、等待到位并读取报警状态。
  02 送空瓶与取瓶：驱动进料、确认传感器、移至空瓶入口及工作点、夹取瓶子。
  03 瓶位检测：检查容器和各相关站位传感器，读取状态与计数。
  04 瓶内冲洗：退到入口、转移至冲洗点，按配置执行冲洗及后续阀门动作。
  05 灌装定位：移至对应口味的灌装入口及工作点，等待到位检测。
  06 灌装：设置容量和灌装时间，启动对应灌装设备，核验流量、液位和压力。
  07 液位复检：在当前位置读取并核验液位，不增加独立“质检移动点”。
  08 封盖：移至封盖点，供盖、触发封盖电机、执行封盖保持并检查扭矩和盖状态。
  09 打码贴标：移至打码点，触发已有打码/贴标输出并检查到位信号。
  10 成品出料：移至成品点、松夹、驱动出料、核验出料信号并更新完成计数。
  11 CIP清洗：完成生产循环后，执行既有清洗、消毒和冲洗动作。
  12 回零待机：关闭输出，定位电机回零并检查报警状态。

每份配方只在开始执行一次01，在循环中重复02—10，在结束执行一次11和12。
三种口味分别运行，每个口味两批、每批六瓶，共12瓶；三份新配方合计36瓶、9000 mL。
这些是模拟过程的配置要求，不是现场产量或实际灌装精度测量值。

新增规格的工程约定
------------------
三种口味索引依次为orange=0、apple=1、grape=2；250 mL规格索引为2。
L4只提供[口味索引,规格索引]，通过配方查找表调用共同流程。
灌装口为OrangeFill、AppleFill和GrapeFill；给定流量分别为200、180、220 mL/s。
时间按ceil(1000×250/流量)计算，分别为1250、1389、1137 ms。
空瓶、冲洗、封盖、打码和成品站可跨口味共用；三种口味使用不同的灌装站点。
点位、流量、封盖方式和设备标识都是预先给定的模拟工程数据，不由模型从容量推断。

生产点位是production_points数组索引；每个点映射为X、Y、Z轴各自0—15的预置PR点号。
PR点号不是毫米坐标，也不能直接用来判断真实路径间距、碰撞间隙或速度。
Y1和Y2使用同一Y轴点号；只触发目标点号发生变化的轴，随后等待到位并刷新位置显示。
预置PR路径的设备调试和写入不属于本次生产流程配置。

当前run_recipe的批次循环固定为2，produce_batch的单批循环固定为6；配方表中也记录2和6。
不要把配方中的batches/units_per_batch误读为已动态驱动循环的参数。
改变生产数量时，需要同时修改并验证相应循环定义，超出本次历史扩展允许的改动范围。

质检、包装和异常处理的边界
------------------------
本例的质量检查由液位复检、封盖扭矩/盖状态以及打码贴标到位检测组成。
它没有独立质量检测站、视觉检测、抽检设备或不合格品剔除与返工支路。
判定失败或超时按现有节点/轮询配置报告对应错误；不能把这些错误报告解释成已经实现自动分拣。

成品出料是本流程与后续包装工序的交接边界；当前配置没有包装机、装箱点或自动装箱动作。
所以表中完整列出的是本例实际建模的十二阶段流程，而不是补写不存在的包装工序。
如要加入装箱或NG处理，应先提供设备、点位、动作及检查规则，再修改配置并重做轨迹验证。

原有配置、新增输出与单体对照
--------------------------
基线为examples/beverage_full/example4：2 L、330 mL两种规格，三种口味，共六份配方。
已保存raw_response.json通过规定的append/replace/create操作应用到基线副本，增加：
  - 16个生产点、3份250 mL配方和相应查找表项；原点位和原配方不变。
  - run_recipe规格索引上限由1扩展为2；其余工艺主体不变。
  - 3个L4入口，各自传入口味索引和规格索引2。
首次原始输出共9项编辑，涉及5个文件；不修改L1/L2实现、设备注册表或原六个L4入口。

单体对照使用预先保存的三份新增规格参考JSON；这些参考由评估侧提供，没有送给历史生成器。
已有六配方的单体完整配置为30893行、四层完整配置为4500行；扩展到九配方后为46295行和4728行。
新增三种口味250 mL时，单体净增15402行，四层净增228行；统计含各自需要的共享定义和数据。
这些数值描述配置文本改动量，不等同于实际工时；完整比较口径及文件变化见comparison.txt。

使用与验证
----------
1. 从仓库根目录打开本目录工作簿，结合动作明细确认三种口味完整的点位、设备、顺序和检查条件。
2. 对照每行来源路径读取实际JSON；不要用口头总结替代动作顺序或异常条件。
3. 在仓库根目录运行：

     python scripts/verify_beverage_process_spec.py

   命令核对来源清单、process_spec.json、工作表数据、CSV和Excel的数据内容是否与配置一致，然后调用原有
   verify_beverage_nl_extension.py，重新应用并验证已保存的首次输出。
   出错时返回非零退出码。检查不会把补充材料登记成旧生成记录的输入，也不会重新生成模型响应。

4. 只检查补充材料与来源一致、不重放模拟时，运行：

     python scripts/verify_beverage_process_spec.py --no-replay

5. 只需重放历史生成输出时，可以单独运行：

     python scripts/verify_beverage_nl_extension.py

   原脚本核对冻结输入、基线与原始输出，检查增量修改边界，运行确定性模拟并保存报告。
   候选配置和新报告写入build/beverage-nl-extension/下新建的独立目录，不覆盖历史文件。

原回放包括九份正常配方、十一种既定故障，以及原六份配方的时间轨迹保持检查。
十一种故障施加在既有orange_family配方，不能表述为每份新增250 mL配方都运行了全部故障。
比较检查单体和四层执行的时间戳、设备操作、响应、状态及完成数量；成功只支持这些已建模场景。
新补充材料不增加硬件实验，不把已有一次生成结果解释为一般生成成功率。

来源与维护
----------
输入与来源：上一级prompt.txt、context.json、generator_instruction.txt、provenance.json。
生成增量：上一级raw_response.json；原报告与差异：validation_report.json、changes.diff。
固定流程：examples/beverage_full/example4/layered/，以及device_registry.json和system_variables.json。
单体参考与比较：examples/beverage_full/example5/legacy/及examples/beverage_full/comparison.json。
执行核对：scripts/verify_beverage_nl_extension.py、scripts/simulate_beverage_full.py。

generation_input.json保存完整原基线依赖，供后续任务读取节点、设备、子过程和原六份配方；
process_spec.json的configuration_documents则保存基线应用已保存增量之后的完整候选配置，供核对输出。
未来修改工艺时，应更新配置和相应说明，重新生成/核对导出数据并保留独立版本。
数据抽取命令为python scripts/build_beverage_process_spec.py，更新JSON和CSV。
Excel的可选重建脚本为scripts/render_beverage_process_spec.mjs，需作者环境中的
@oai/artifact-tool；已发布Excel的验证只需Python标准库，不依赖该渲染工具或Excel软件。
若开展新的自然语言生成，使用generation_input.json和requirements_250ml.txt，
不提供含候选答案的工作簿或process_spec.json，并记录新输入及哈希、新生成来源和首次原始输出，
再单独验证；不要覆盖本例已经冻结的一次生成证据。
